# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Lasso is a Go backend (`src/main.go` and friends) that serves a React/TypeScript SPA. All Go code lives under `src/` (the Go module root — `src/go.mod`). The frontend in `src/web/` is **built and embedded into the Go binary** — `go build` embeds `src/web/dist/`, so it must exist locally (run `mise run build`) but is **not** committed (it's gitignored). CI builds the frontend and produces release binaries.

## Commands

Backend (run from repo root, via [mise](https://mise.jdx.dev); Go sources are in `src/`):
- `mise run build` — builds the frontend then `go build` in `src/` (binary → `./lasso`)
- `mise run dev` — Vite dev server with HMR, proxying to the Go backend (requires tailscale up; auto-bumps the dev port from 8190 if busy)
- `mise run test` — `go test .` in `src/`
- `mise run typecheck` / `mise run lint` / `mise run check` — the frontend checks (typecheck and lint also cover the OpenBot example plugin)
- `mise run openbot:build` / `mise run openbot:check` — build the OpenBot example plugin's page into `examples/plugins/openbot/ui` (committed, so the plugin needs no build to install) / biome-fix it
- `mise run icons` — re-render the favicons and home-screen icons from the raster mascot in `brand/icon/`
- `mise run diagram` — render `docs/assets/architecture/*.reladraw` to SVG, in the `sandbox` incus container
- `mise run dev:containers` — list the per-worktree dev containers, the worktree each belongs to, and whether it still exists
- `mise run dev:prune` — delete dev containers whose worktree is gone (dry run; `-y` to act). Never touches one whose worktree exists

**Every frontend command runs inside this worktree's own incus dev container, not on titan.** `bun install`, Vite, tsc and biome are all third-party code, and on the host that code would run as the logged-in user next to the SSH key, the 1Password session and the tunnel credentials. The mise tasks above handle this for you — see `scripts/container.sh`. Do **not** reach past them and run `bun` directly in `src/web/`; that puts the dependency tree back on the host and is exactly what the container exists to prevent. The Go half (`build`, `test`) still runs on the host: Go has no install hooks, and the binary has to be here anyway to drive herdr.

**The containers are declared in `scripts/isb/*.yaml` and driven by [isb](https://github.com/execution-associates/isb)**, not by hand-rolled `incus` calls. isb talks to incusd over its unix socket with a deadline on every step, never the incus CLI (`incus init` reads instance YAML from a non-tty stdin, so under an agent whose stdin is an inherited socket it blocked forever before reaching the server — 11 minutes, no operation), creates a container with every mount and label in one request before its first boot, and on `up` only touches a device that is wrong — re-adding a correct one remounts it and silently kills a running Vite's inotify watches. isb is NOT pinned in `mise.toml`: the tasks use whatever `isb` is on the host's PATH and `require_isb` refuses anything older than 1.0; never `cargo install` it on a host — build.rs is arbitrary code. `dev.yaml` is the container; `bun-cache.yaml`, `dev-web.yaml` (the Vite `command:` and the two proxy devices for `mise run dev`), `icon.yaml` and `openbot.yaml` (`examples/plugins/openbot`, for `scripts/container-openbot.sh`) are overlays that `container.sh` adds with `container_with`. `sandbox.yaml` is the separate `sandbox` container for `mise run diagram`. The shell scripts only compute the per-worktree name and paths, export them for the YAML's `${VAR}`s, and call `isb up -d` / `isb exec`. **Since isb 0.4 a bare `isb up` stays in the foreground, like `docker compose up`**: it runs each service's `command:`, then stops the sandboxes when every command has exited, on SIGINT/SIGTERM/SIGHUP, when stdout closes, or when any process that started isb exits (it polls its ancestors every second). So every task that runs `up` and then carries on with `isb exec` must use `up -d` (`container_ensure`, `sandbox_ensure`), or it hangs at `up`. The one foreground `up` is `mise run dev`: Vite is `dev-web.yaml`'s `command:`, run by `container_up_foreground` after a `container_ensure`, so the container stops when Vite exits, on Ctrl-C, or when whatever launched the task goes away (an agent's background task included), and the script's trap and the dev task's backend unwind behind it. Stopping means the dev server's end also stops the container under any other task in that worktree at that moment; the next task starts it again. A dev run killed outright never runs its trap, so its `backend`/`vite` devices stay on the stopped container; `container_ensure` reaps them before every other task's `up -d` unless the dev session's `flock` (held for the life of `container-dev-web.sh`, dropped by the kernel even on SIGKILL) says one is alive. That lock is also what refuses a second `mise run dev` in a worktree. Add a mount or a setting in the YAML, not with `incus config`: isb leaves devices it was not told about alone, so a hand-added one silently drifts.

**One container per worktree**, named `dev-lasso-<worktree>-<hash of the src/web path>` and mounting only that worktree's `src/web` (plus `brand/icon` for `icons`). A single shared `dev-lasso` used to be re-pointed at whichever worktree ran a task last, which unmounted the tree under another worktree's running Vite (Rolldown "Failed to get current dir" → SIGABRT). `node_modules` lives in each worktree's own `src/web`; only bun's download cache is shared, via the `lasso-bun-cache` incus volume, so a new worktree's first task takes ~30-40s rather than a cold download. One `mise run dev` per worktree (a second is refused); several worktrees' dev servers run side by side, each on the next free loopback port from 5173, published over HTTPS on the same port by `tailscale serve` (`scripts/container-dev-web.sh`). `LASSO_DEV_CONTAINER` pins a name and brings the old sharing back with it. The per-worktree lock is isb's (`$XDG_RUNTIME_DIR/isb/…`). A container is deleted only once its worktree is gone: on titan the weekly `lasso-prune` timer (titan-iac `tools/lasso-prune.sh`) does it right after archiving stale worktrees, and `mise run dev:prune -y` (`isb prune --label lasso.worktree --missing-path`) does it on demand. The old shared `dev-lasso`/`dev-lasso-2` show as `legacy` and are never pruned; `isb rm` them by hand once nothing runs in them.

Underlying bun scripts, for reference (invoke via the mise tasks, not directly):
- `bun run dev` / `bun run build` (`tsc -b && vite build`)
- `bun run typecheck` — `tsc -b`
- `bun run lint` — `biome lint .`
- `bun run format` — `biome format --write .`
- `bun run check` — `biome check --write .` (format + lint fixes + import/class sorting)

## Frontend workflow

- Run `mise run typecheck` (`tsc -b` — the project references mean a bare `tsc --noEmit` checks *nothing*, since the root tsconfig has `files: []`) and `mise run lint` before considering frontend work done.
- `src/web/dist/` is the embedded bundle — gitignored and not committed. Run `mise run build` to regenerate it locally; CI builds it for releases.

## Formatting & linting

Tooling is **Biome** (`src/web/biome.json`) — it replaced Prettier + ESLint. Style: 2-space indent, no semicolons, double quotes, ES5 trailing commas, 80-col width. Tailwind class sorting is handled by Biome's `useSortedClasses` (aware of `cn`/`cva`). a11y rules are demoted to warnings (not previously enforced); don't treat them as blocking. Go code: standard `gofmt`.

## Security gotchas

- Never bind to `0.0.0.0`. Use loopback or the tailscale IP. For non-loopback access set `UI_AUTH=user:pass`.
- The file endpoints (`/api/file`, `/api/files`, and the write/rename/delete/upload trio) read and write arbitrary absolute paths as the running user — on the calling tab's host, or on any host lasso may drive when the request names one (`?host=` / a `host` field; see "File viewer host"). Safe only on a private tailnet.
- Running lasso nested inside herdr requires `allow_nested = true` in `~/.config/herdr/config.toml`.
- `/api/push/subscribe` records a URL lasso will POST to unattended, so it is gated by `UI_AUTH` like the rest of the app (deliberately NOT in `withAuthExcept`) and refuses anything that is not `https` with a valid P-256 key. A stored endpoint is a bearer capability to push to that device: it is never returned to a client and never logged — the Settings list and the logs both identify a device by a digest of it (`pushDeviceName`).
- `/cdp` (the shared browser, see "Browser tab and the shared browser") is full control of a real Chromium — every page, every login in its profile — and follows `/mcp`'s trust model: exempt from `withAuthExcept`, gated by `withCDPAuth` (open by default; UI_AUTH basic when set; `/mcp`'s bearer/basic rule plus a `local`-reach scope check when `MCP_OAUTH` is set). Because the proxy strips `Origin` for Chromium, `cdpOriginAllowed` must refuse a foreign Origin **before** anything else — it is the only thing keeping an arbitrary web page from driving a loopback lasso's browser. `GET /cdp/browsers` is lasso's own listing on that surface (not a passthrough): every browser and the CDP address to connect to each, so a client that speaks only CDP discovers them with no MCP server (`/cdp/profiles` answers the same list under a `profiles` key). It never starts a browser.
- `/herdr-mcp` (`src/herdrmcp.go`, `docs/mcp/herdr-mcp.md`) is herdr's socket API as MCP tools, one per method, generated from `herdr api schema --json` with herdr-mcp's tool names (`pane.list` → `pane_list`) and reloaded when the schema's digest moves. It takes `/mcp`'s gate exactly (`withMCPAuth`, exempt from `withAuthExcept`) and every call runs `callerFrom(req).requireHost` before `resolveBackend`, so a per-host credential reaches the same hosts it does on `/mcp`; `machine` is only an alias of `host`. No queue of its own: each call dials herdr fresh (`herdrCallWithin`) and remote hosts ride hostBackend's pool.
- The `browser_*` tools on `/mcp` (chrome-devtools-mcp bridged, see "The browser tools on `/mcp`") are a front door to `/cdp`, so each CALL meets `/cdp`'s standard, which is stricter than `/mcp`'s: a foreign Origin is refused (`cdpOriginAllowed`, credentials or not), **UI_AUTH basic is required under UI_AUTH alone** (where the rest of `/mcp` is open), and under `MCP_OAUTH` the credential's reach must include `local`. `withBrowserToolGate` (inside `withMCPAuth`) computes the HTTP half on every `/mcp` request and stamps a per-process secret (`browserGateToken`) or a refusal into headers the SDK copies onto the call; `forward` checks it plus `requireLocalBrowser` and answers a tool error (`IsError`) before anything spawns. Both headers are deleted and set on every request — never trust a client's. Their children reach `/cdp` on `internalCDPToken`, which `withInternalCDP` honors ahead of every gate (the Access header gate included) and on `/cdp` paths only.
- The `/mcp` MCP server is **unauthenticated by default** (exempt from `UI_AUTH` via `withAuthExcept`) — it lets any client that can reach lasso spawn and drive agents. Same trust model as `/api/file`: safe only on loopback / a private tailnet, or behind an edge auth gate (e.g. Cloudflare Access). It introduces no new binding. Set `MCP_OAUTH` (below) to gate it in the origin instead.
- **Unless `MCP_OAUTH` is set**, the origin deliberately implements **no** OAuth (no `.well-known`, no `401`/`WWW-Authenticate`). So OAuth-based MCP clients (Claude Desktop / claude.ai connectors) connecting to `/mcp` over the public hostname require **Managed OAuth enabled on the Cloudflare Access app** — Access then acts as the OAuth 2.1 authorization server (Dynamic Client Registration + auth-code/PKCE), runs the login against the existing Access policy, and issues tokens; the origin still sees an authenticated Access session and needs no auth code. Without it the client's registration fails ("Couldn't register with lasso's sign-in service"). This is an edge setting on the Access application, not a `cloudflared`/tunnel change. `oauth.go` keeps every OAuth route 404 while `MCP_OAUTH` is unset precisely so this Access path stays intact — don't make that metadata unconditional.

## MCP OAuth (`src/oauth.go`)

`MCP_OAUTH=client_id:client_secret` (environment only, like `UI_AUTH` — never argv) turns lasso into a small OAuth 2.1 authorization server for its own `/mcp` resource. Unset = today's open `/mcp`, unchanged.

- **Grants**: `client_credentials` (machine-to-machine — scripts, CLIs, Claude Code; restricted to the `MCP_OAUTH` client and to per-host clients minted with `lasso mcp-client add`, never to an open-DCR registration) and `authorization_code` + PKCE/S256 with `refresh_token` rotation. claude.ai / Claude Desktop custom connectors **cannot** use `client_credentials` — Anthropic's connector infra requires `authorization_code`+`refresh_token` and per-connection user consent — so their "Advanced settings → OAuth Client ID / Client Secret" fields are a *pre-registered client for the auth-code flow*. That's why both grants exist.
- **Routes**: `/.well-known/oauth-protected-resource`, `/.well-known/oauth-authorization-server`, `/oauth/register` (open DCR), `/oauth/token` — all exempt from `UI_AUTH`, since they're the credential-less half of the handshake. `/oauth/authorize` is **deliberately gated** by `UI_AUTH`/Access: that human gate is what makes open DCR safe (anyone may register; nobody gets a token without passing the door and clicking Approve).
- `/mcp` accepts **either** a bearer token **or** the `UI_AUTH` basic credentials, so the CLI and existing callers keep working without an OAuth dance.
- Redirect URIs: DCR clients get exact matching. The pre-registered client accepts any https/loopback callback (a connector's callback isn't known when the secret is minted) and the consent screen displays the exact target; set `MCP_OAUTH_REDIRECT_URIS=<comma-separated>` to lock it to an allowlist.
- Codes and tokens live in `oauth_*` tables in `lasso.db`, stored as SHA-256 hashes, so refresh tokens survive restarts and self-updates.


## Design notes (`docs/design/`)

Each subsystem's full rationale lives in `docs/design/<topic>.md`. **Read the matching file before changing that subsystem**: most of the rules there exist because the obvious version was tried and broke. The one-liners below are only the invariants that are easiest to violate.

- **Per-tab hosts** → `per-tab-hosts.md` (`reqhost.go`, `hostfeed.go`, `switch.go`, `lib/host.ts`). The host is a property of the browser TAB (`X-Lasso-Host` / `?host=`, sessionStorage), never a process global; `POST /api/host` attaches, it switches nothing. One feed per watched host, stopped when idle (the default host is exempt). The `pane.list` cache is keyed per host.
- **Theme atmosphere, appearance, palettes, legibility** → `theme-atmosphere.md` (`index.css`, `lib/theme.ts`, `lib/wallpaper.ts`, `lib/mode.ts`, `db.go`, `legibility.go`, `agentsync.go`). Backdrop and appearance are SERVER state in `ui_state`, merged per theme and per field; no `localStorage` for them, and no import from the old keys. `applyAtmosphere` is the single repaint chokepoint. Translucency is `background-color` alpha, never `opacity`. Only `setMode`/`setPalettePref`/the OS flip push a palette to the fleet, never `refreshTheme`. Never send `appearance_mode: ""`. The "did lasso write this theme" record is SHARED through `lasso.db` (`theme_written:<host>`, `theme_hub`), never per-process memory: a dev and the production lasso on one db must reach the same adopt/converge decisions or they revert each other.
- **Sidebar-layout ownership and the `ui_state` write pipeline** → `sidebar-layout.md` (`uilock.go`, `lib/sidebar.ts`, `lib/ui-state.ts`). `sidebar_collapsed`/`sidebar_pct` are arbitrated by an in-memory claim: only a client stamping `user_intent`, or the current owner within its lease, may move them. One `ui_state` save on the wire at a time.
- **Agent visibility scope and groups** → `agent-scope.md`, runbook `docs/mcp/agent-scope.md` (`hostscope.go`, `callerscope.go`, `groups.go`). Caller identity comes from the token, never an argument; `host` defaults to the caller's own host. Containment requires `MCP_OAUTH`.
- **Agent record reconciliation** → `agent-records.md` (`agentreap.go`). Records are tombstoned (`closed_at`), not deleted, and only from a successful, non-empty, per-host enumeration after `agentReapMisses` consecutive misses. Foreign herdr panes are never touched.
- **File viewer host, herdr machines, `open_file`** → `file-viewer-host.md` (`panehost.go`, `agentcwd.go`, `clientmachine.go`, `openfile.go`). The sidebar follows the FOCUSED pane's cwd and the host it lives on (ssh-attach and machine hops included). Every file endpoint takes a host; half a cutover means an editor saving to the wrong machine.
- **Chat view** → `chat-view.md` (`chatview.go`, `codexchat.go`, `transcriptlog.go`, `ChatView.tsx`, `AgentSidebar.tsx`, `AgentsTab.tsx`, `lib/agents.ts`). An overlay over a still-mounted terminal, read from transcript files, never the PTY. A pane id is never carried across a hop. The log follows the SESSION (`transcripthost.go`): when the pane's host lacks it, other hosts are asked within a 1.5s budget and `served_by` names the one read, while `host` stays the pane's; a `local` pane is never searched for. Logs are paged line-by-line (`readLogPage`) because inlined images make single records huge.
- **Bots** → `bots.md` (`bots.go`, `botavatar.go`, `botenv.go`, `botkey.go`, `botoauth.go`, `claudesessions.go`, `botruntime.go`, `botsapi.go`, `mcp_bots.go`, `BotsView.tsx`, `BotSettings.tsx`). A bot is a `bots` row plus a folder whose `mise run bot` is BOTH the launch and herdr's `resume_argv`, so a restore gets the same env, secrets and per-channel grants. Env is fnox's, granted to that task alone by mise's `[secrets.fnox]`. Lasso writes `fnox.toml` once (default provider `lasso`, age, keyed to lasso's own per-install `<lassoDir>/age.txt`) and then only through the fnox CLI with values on stdin, so a human can swap the provider. The task is `interactive` (secrets otherwise take the TTY away) and its `secrets` list is regenerated on every env change. Lasso never writes the bot's own `mise.toml` and never overwrites `CLAUDE.md`. MCP OAuth is lasso's (`botoauth.go`): lasso runs discovery, DCR and PKCE, with the redirect to its own `/api/bots/oauth/callback` or a pasted localhost address. Tokens live in the bot's fnox as `LASSO_OAUTH_*`, which are never granted to the task, and claude reads them through `headersHelper`. Only non-secret metadata goes in `bot_mcp_oauth`. The task script answers the trust and dev-channel dialogs and claims the herdr name itself. Resume reports carry source `lasso`, agent `claude` and a rising `seq`. A bot is found by herdr agent name, and only in its own folder (another agent may hold the name), never a stored pane id. `launch_task` picks the mise task every start, restore and self-restart goes through; lasso writes only `bot` and `restart`, and a mode (another provider, say) is the human's task that sets env and ends `exec mise run bot -- "$@"`. A save naming a task the folder lacks is refused. Keep-running waits 6 ticks so herdr's restore wins, and one lasso per `lasso.db` runs the loop (`bots.runner.lock`). A bot configures itself through `/mcp` (`get_bot`, `update_bot`, `set_bot_env`/`unset_bot_env`, `set_bot_avatar`, each behind `requireHost`): every `local` bot's generated `mcp.json` gets a `lasso` server at this lasso's own listen address, never for another host's bot, never under `MCP_OAUTH`, and a human-named `lasso` wins. Creating and deleting stay human-only. A picture is raster only, sniffed by content, never SVG (`botavatar.go`), and a settings PUT decodes over the stored row. **Jobs** (`botjobs.go`, `botjobcmd.go`, `botchannel.go`, `cron.go`, `mcp_botjobs.go`, `BotJobs.tsx`, `lib/cron.ts`) reach a bot through `lasso-channel`, which is `lasso channel --bot <name>` written into every local bot's mcp.json (0600, it holds the bot's channel token). A channel must be a stdio process claude spawns, so it can never be a route on `/mcp`. `/bot-channel/` and `/hooks/bots/` are exempt from UI_AUTH and carry their own credentials (the channel token, the job's webhook key). A job with a `command` is a watch: each firing runs it in the bot's folder with a systemd-user-like env (never lasso's credentials), silence delivers nothing, output runs APPEND to the undelivered watch event under per-run headers (never overwrite), failures are damped 1/2/4/8… plus one recovery notice, one run per job at a time, and a stopped bot's watch does not run. Delivery is claim/notify/ack, firings merge into one undelivered event with a count, a stopped bot's firings are dropped (never queued), and only the runner-lock holder fires schedules. The loop pushes `bot_message` (tag `bot:<name>`, `url` `/bots/<name>`, icon = picture) when a `notify` bot goes idle on a new message of its own, the first sighting after boot being a baseline; `sw.js` skips one whose chat is focused and visible, never on iOS. Under `/bots`, `main.tsx` swaps in `manifest-bots.json` client-side (so Vite serves it too), and a standalone window there or `?app=bots` boots `BotsApp`, the Bots view alone, decided once at boot. The compact switcher follows the view's own width (760px), not the viewport.
- **The input dial** → `input-dial.md` (`lib/mobile-input-dial.ts`). Lives inside the ttyd document (keeps the iOS keyboard up). Mounts on coarse pointer OR a PARENT viewport below `md`, both watched, mounted once.
- **Browser tab, lasso's browsers, `/cdp`, the `browser_*` tools, terminal links** → `shared-browser.md` (`browser.go`, `browserprofiles.go`, `cdpproxy.go`, `browsermcp.go`, `mcp_browser.go`, `mcp_browser_profiles.go`, `BrowserTab.tsx`, `LiveBrowser.tsx`, `lib/cdp.ts`). No Go websocket library; lasso proxies CDP and never parses it. `cdpOriginAllowed` runs before the Origin strip, always. Everything a human or agent reads says **browser** (`list_browsers`, `create_browser`, `update_browser`, `delete_browser`, a `browser` argument on every tool); the code and storage say *profile* (`settings.browser_profiles`, `/api/browser/profiles`, `<lassoDir>/browser-profiles/<id>`) and keep it, so stored browsers load unchanged. chrome-devtools-mcp's tools are on lasso's own `/mcp` as `browser_<name>` (registered on `sharedMCPServer` from a per-process tool-list cache; a missing or broken chrome-devtools-mcp means no browser tools, never a failed initialize); each takes `browser`, resolved at call time, unknown = tool error, never a fallback. A session holds one chrome-devtools-mcp child per browser it has USED, keyed by the call's `ServerSession`, spawned on first call and dialing lasso's own `/cdp` (or `/cdp/p/<id>`); the session's end (`ServerSession.Wait`) or 30 minutes without a browser call stops them; a browser's stop closes only its children; no cap by default. A browser is its own Chromium process (cookies can't be per-context and persistent). lasso configures no proxy for any browser. A browser with a `cdp_url` is a REMOTE browser (`browserremote.go`): lasso dials its DevTools endpoint, never launches or stops it, re-reads `/json/version` to notice restarts, and accepts an id-less `/devtools/browser` (Kitesurf) as well as `/devtools/browser/<id>`. No `npx` fallback, never auto-`--no-sandbox`.
- **Notifications / Web Push** → `notifications.md` (`notify.go`, `webpush.go`, `notifywatch.go`, `sw.js`, `lib/push.ts`). Stdlib-only Web Push; the VAPID key must never change. Only 404/410 deletes a device. `sw.js` caches nothing and has no fetch handler. `notify` must report honestly whether anything took it.
- **`lasso mcp` CLI and `lasso connect`** → `mcp-cli.md` (`mcpcli.go`, `connect.go`). CLI flags are built from the schema the SERVER advertises, never a local table; omitted flags are absent, not zero. Test `connect` with `HOME`/`XDG_CONFIG_HOME` pointed at a temp dir, never a real home.

## Plugins (`src/plugins.go`, `src/pluginchat.go`, `src/plugininstall.go`, `src/pluginappearance.go`, `src/pluginmcp.go`, `src/pluginsandbox.go`, `src/plugincli.go`, `src/web/src/lib/plugins.ts`, `src/web/src/lib/sidebar-tabs.ts`, `src/web/src/components/PluginTab.tsx`, `docs/plugins/authoring.md`)

A plugin is `<lassoDir()>/plugins/<name>/plugin.json`: sidebar tabs (its own web page), a stdio MCP server whose tools are mirrored onto `/mcp` as `<plugin>__<tool>`, themes and fonts — any mix. `docs/plugins/authoring.md` is the authoring guide, `examples/plugins/hello` a working tabs+MCP one and `examples/plugins/harbor` an appearance-only one. The design is the trust model; everything else follows from it.

- **A manifest is self-asserted, so it grants nothing.** A new plugin is `disabled`; enabling approves exactly the permissions the listing showed, stored as a **fingerprint** (`pluginManifest.fingerprint`: tabs' entry/url, image, command, network, env KEYS, secrets and their hosts — canonicalized so reordering is not a change, argv order excepted) in the `plugins` settings key. A manifest edit touching any of that reads `needs_approval` and unloads the tabs and the server until re-approved; version/description/label/icon are deliberately outside it, since re-approving typo fixes trains a human to click through approvals. `POST …/enable {fingerprint}` refuses (409) when the manifest changed between the listing and the click. The directory is rescanned every 10s and on every `GET /api/plugins`, which is what makes an in-place edit take effect with nobody pressing Reload.
- **Trusted and VM are the operator's flags, never the manifest's** — "run me on the host" is exactly what a hostile plugin would ask for. Both live beside the approval (`pluginGrant.Trusted`/`.VM`), survive a disable, and a flip is a restart (`pluginIsolation`: host > vm > container; a server cannot move between them in place, and a VM flip while trusted changes nothing running). A manifest may name `mcp.vm_image` (in the fingerprint, `omitempty`) but cannot ask for a VM. A trusted child still gets `minimalChildEnv` (the `browserMCPEnv` allowlist, factored out) plus its own env and secrets — never `UI_AUTH`/`MCP_OAUTH`/`LASSO_MCP_TOKEN`.
- **`/plugins/<name>/` is behind UI_AUTH and every response — 404s included — carries `Content-Security-Policy: sandbox allow-scripts allow-forms allow-popups allow-modals allow-downloads`.** The CSP sandbox is what makes the document an OPAQUE origin even opened top-level; without it plugin JS is same-origin with lasso and can drive `/api/file` with the human's cookies. Never add `allow-same-origin`. Paths go through `cleanPluginPath` (no `..`, no hidden segments — a plugin dir may hold a `.env`) and then `os.OpenRoot`, which is the check that sees symlinks. Only enabled plugins are served; everything else is an unexplained 404.
- **A tab talks to lasso only over `postMessage` (`lasso-plugin/1`), and the PARENT is the identity**: it routes by which iframe sent the message (origin is "null" for every sandboxed frame, so it identifies nothing). `POST /api/plugins/<name>/call` therefore trusts the NAME in the path — the parent put it there — and allows only tools in THAT child's own list, by either spelling; `beta__x` from alpha's tab is 403 even though it is a real tool.
- **One long-lived child per plugin, on the SHARED `/mcp` server** (`sharedMCPServer`, set in `newMCPHandler`), unlike the `browser_*` tools' child per session per browser: a plugin's tools are lasso's tools, every session sees one list, and `AddTool`/`RemoveTools` make the SDK send `tools/list_changed`. Forwarding is browsermcp.go's (raw arguments in, the child's `CallToolResult` out untouched, non-object schemas skipped). Every call requires `callerFrom(req).allows("local")`, the `shared_browser` rule, answered as a tool ERROR (`IsError`), not a JSON-RPC one. A dead child loses its tools, restarts with backoff (1s→60s, reset after a long healthy run), and re-adds them; `unavailable` (no isb >= 1.0, `isb serve` down, an unresolvable secret) waits for the operator's Restart instead of looping.
- **The sandbox is an isb 1.0 sandbox `lasso-plugin-<name>`** (labels `owner=lasso`, `lasso.plugin=<name>`, outside every org — `isbEnv` strips `ISB_ORG`/`INCUS_PROJECT`/`ISB_URL`/`ISB_TOKEN`). `isbCreateArgs`/`isbExecArgs` are pure and tested. Container: `docker:<image>` (explicit `docker:`/`ghcr:`/`quay:`/`oci:`/`images:` kept), `--idmap auto`, and an OCI init of `sh -c "sleep infinity || exec tail -f /dev/null"` — the image's own CMD exits without a tty and takes the instance with it, so the image must have `sh` + `sleep`/`tail`. VM: `--vm`, `vm_image` or `images:ubuntu/24.04/cloud`. The server is `isb exec -i -T -w /plugin -u 1000:1000 … -- <cmd>` run as lasso's child (setpgid + Pdeathsig): isb 1.0 forwards stdin ONLY with a tty, `-i` or `-T`, so dropping them gives the server EOF at once. Uid 1000 in the VM too: virtiofs shares `/data` with NO uid translation, so guest root would create host-root-owned (even setuid) files there (measured).
- **No liveness ping.** `isb exec` exits within ~0.2s of the server inside dying, container and VM alike (measured on isb 1.0.0), so `proc.done()`/the session closing is the signal; `serve` sets the error status BEFORE `proc.stop()`, since removing a sandbox takes seconds. stderr streams through exec into the per-plugin `lineRing`.
- **Egress and secrets are isb's** (`--egress host:port` per network entry and per secret host on 443, `--egress none` when there is neither). isb refuses IP literals and single-label wildcards, so `checkPluginHost` makes them an invalid manifest. Secrets are resolved from lasso's env, else `secret NAME` (10s), and written on STDIN (`isb secret set <store> -`, never argv) under `lasso-plugin-<name>.<secret lowercased>` (the `.` cannot occur in a plugin name, so one plugin's prefix never matches another's; secrets differing only in case are invalid), passed as `--secret NAME=<store>@hosts`. The proc's stop deletes the store entries it wrote; uninstall/unlink also `purgePluginSecrets` by prefix. isb's proxy refuses connections from the host: test egress/secrets from INSIDE a sandbox.
- **One lasso per plugins directory runs the servers** (`pluginlock.go`): an `flock` on `plugins/.runner.lock`, taken in every `reconcile`. Two lassos sharing a `LASSO_DIR` (titan's dev 8190 and production 8090 both read `~/.lasso`) share the approvals, so both would reconcile the same plugins onto the same fixed `lasso-plugin-<name>` sandbox and isb store names, and each launch's `isb rm -f` would delete the other's sandbox forever. The loser still serves tabs, themes and fonts (files) and lists each server `unavailable` naming the holder (pid + listen address, written into the lock file); the kernel drops the lock when the holder exits, even on SIGKILL, and the survivor takes over on its next rescan. `stopAll` releases it after the servers are down.
- **Availability gate** (`currentSandboxStatus`): `LASSO_ISB` (path, PATH name, `off`; when set, nothing else is tried), else the first of `isb` on PATH and the newest mise install that is >= 1.0.0 (`isb --version`, cached per binary mtime), AND `isb serve`'s `/healthz` over its unix socket (`$ISB_SERVE_SOCKET`, else `$XDG_RUNTIME_DIR/isb/serve.sock`) — a sandbox created while the daemon is down has a dead network. The isb CLI needs the daemon's `XDG_STATE_HOME` (they share each sandbox's egress CA). Every launch first `isb rm -f`s the name (a crashed lasso leaves one), every stop does it again, and shutdown calls `plugins.stopAll()` synchronously after `browserMCP.closeAll`. Boot runs `sweepLegacyMSBSandboxes` (stop+rm any `lasso-plugin-*` microsandbox VM a 4.x lasso left; quiet when msb is absent).
- **`sidebar_tabs` in `ui_state`** is the right sidebar's order and hidden set: `[{id, hidden}]`, built-in ids (`sidebarBuiltinTabs`) and `plugin:<name>:<tab>`. Replace-on-write (one Settings screen edits it), validated (≤64 entries, ids 1-100 chars, no dupes → 400 like `browser_mode`), and `settings` is forced visible — it is where a hidden tab is un-hidden. It is detached before the patch decode like the atmosphere collections: the JSON decoder reuses a slice's backing array, so decoding over `stored`'s would edit `stored` and make the no-op check skip the save. Ids for plugins that are gone are KEPT so a re-enabled plugin comes back where it was.
- **The client side of the bridge is `lib/plugins.ts:attachPluginBridge`, one per iframe.** It answers a message only when `event.source` is ITS frame's `contentWindow`, takes the plugin name from its own closure (never from the message), and serves a fixed method list (`context.get`, `theme.get`, `fonts.get`, `file.open`, `tool.call`, `chat.read`, `chat.send`, `chat.answer`, `chat.stop`, `toast`) — anything else is "unknown method". Replies and pushes go out with targetOrigin `"*"` (an opaque origin cannot be named), so nothing secret may ever be in one. Toasts are text-only, 200 chars, 5 per 10s; at most 8 requests in flight per frame. `PluginTab`'s iframe `sandbox` must match the server's CSP list — the attribute is the ONLY sandbox a `url` tab has, lasso not being its server.
- **`views` are main-window pages** (the footer's view menu, after Terminal/Chat/Grid): same `pluginTabSpec`, validation (`validatePluginPages`, ≤8), serving, sandbox and bridge as tabs, framed by the same `PluginTab` with `placement: "main"` (in the bridge's context). Their entries/URLs are in the fingerprint under an `omitempty` `views` key, so a view-less plugin keeps the fingerprint it was approved under, and moving a page from `tabs` to `views` is a re-approval. The left view id is the global id `plugin:<name>:<id>` at `/view/<name>/<id>` (`lib/url.ts`); it overlays the terminal like the chat (never unmounts it), mounts on first show and then stays mounted invisible, and falls back to the terminal once the listing has answered without it. The grid and plugin views have no left sidebar (`noLeftSidebar`), so the footer's left toggle and ⌘B are off there. Below md the dial's Chat button opens the view picker once any plugin view exists, and a plugin view carries its own picker button in the dial's corner (`input-dial.md`).
- **Theme sharing is data over the bridge, never lasso's CSS** (`lib/plugin-theme.ts`, `src/pluginsdk/`). `theme` carries `dark`, the terminal `colors`, `tokens` (an ALLOWLIST of lasso's custom properties, `PLUGIN_THEME_TOKENS`, read computed) and `fonts_key`; `fonts.get` hands over the Latin font faces' BYTES (the parent fetches them same-origin and authed; the opaque frame could not: CORS mode, and behind auth), which the page registers with `FontFace`. One shared `MutationObserver` on `<html>` attributes and `<head>`, plus `onThemeApplied` for the module-state palette, triggers a push, diffed per frame. The SDK (`/plugins/_sdk/lasso.js` + `lasso.css`, `go:embed`, served by `serveFiles` with the same CSP before the name check; `_sdk` cannot be a plugin name) applies it under lasso's own names and only via `setProperty` with names matching `^--[a-z0-9-]{1,64}$`.
- **`agents` is the chat grant** (`pluginchat.go`): `[{name, host?}]`, a herdr agent NAME per entry, in the fingerprint under an `omitempty` `agents` key (host canonicalized to `local`, sorted, deduped). The bridge's `chat.read/send/answer/stop` go to `/api/plugins/<name>/chat[/send|/answer|/stop]`, which trusts the plugin name in the path like `/call`, checks the ENABLED plugin's grant covers `(agent, host)` server-side on every call, and resolves the pane from herdr's `agent.get` with the answer's own `name` required to match (a pane id is never a grant). Everything after resolution is the chat view's own code (`buildChatPayload`, `chatSubmit`, `chatAnswer`); stop is one `Escape`, refused unless herdr or the transcript says the agent is working. The page side follows `file.open`: send/answer/stop need the frame on screen, read does not. A plugin's read passes `withIncoming`, which adds Claude Code channel deliveries (`isMeta` user turns with `origin.kind: "channel"`) as `kind: "incoming"` rows; lasso's own Chat view does not ask for them.
- **Plugin pages must load classic scripts.** A `type="module"` script is a CORS fetch, which an opaque-origin page cannot make even from lasso itself; a bundler emits an IIFE (see `examples/plugins/openbot/web/vite.config.ts`).
- **A `url` tab gets no bridge.** It is someone else's site framed as-is; handing it `tool.call` would let any page a manifest names drive that plugin's backend.
- **`file.open` goes through `lib/open-file.ts:requestOpenFile`**, the entry point an agent's `open-file` SSE event now shares, so a plugin gets the same dirty-draft protection in `FilesPanel` and cannot replace unsaved edits. It is refused while that plugin tab is not on screen (selected, sidebar open, document visible) — the same "only a visible tab acts" rule, since a tab nobody is looking at must not rearrange the screen.
- **The strip is resolved, not declared** (`lib/sidebar-tabs.ts`): built-ins plus enabled plugins' tabs, ordered and filtered by `sidebar_tabs`, a real tab missing from the stored list slotting into its default position (plugins before Settings). **A hidden tab still opens when something needs it** — an agent's `open_file` reveals Files, a terminal link reveals Browser — and stays in the strip until another tab is picked; falling straight back would jump away from what was just opened. When the selected tab vanishes (hidden, plugin disabled) the view drops to Files, or the first visible tab, skipping Agents at md+ where it is not rendered. Plugin panes mount on first selection and stay mounted, like the built-ins, so switching away does not reload a plugin's page.
- **Enable sends the fingerprint the dialog showed** (the `Plugin` snapshot taken when it opened), so a manifest edited while the human was reading is a 409, not an approval of permissions nobody saw.
- **`plugins_rev`** rides every SSE frame like `ui_state_rev` (`hub.bumpPluginsRev` → `pushCurrent`); the manager bumps it when the listing's JSON changes, which includes an MCP status transition.
- `findMCPTool` (mcpcli.go) now prefers an EXACT name before the kebab/snake normalization: a plugin may serve both `get-x` and `get_x`, which normalize to one spelling.
- **Appearance is data, never CSS** (`pluginappearance.go`). A plugin that could ship CSS could hide the approval dialog's warnings or paint a fake prompt, so it contributes OPTIONS — a theme (an Omarchy theme dir) or a font (family + files) — and lasso composes every byte of CSS from validated values. **`pluginFontFamilyRE` (`^[A-Za-z0-9 _-]{1,64}$`) is the injection guard** for the family string the frontend writes into `@font-face`/`font-family`; never loosen it.
- **A plugin theme joins the ONE registry** (`reloadOmarchyThemes`, via the `pluginThemeRefs` snapshot the manager publishes — an atomic, so omarchy.go never takes the manager's locks), so it paints chrome, terminals, herdr's config.toml, agent theme files and the fleet sync with no parallel path. Its key is its `id`. Precedence is built-in > official > installed > plugin; a taken key (or an alias spelling of one) is SKIPPED with a per-plugin `warnings` entry and `key_taken`, never an invalid manifest, and between plugins the name that sorts first wins. Catalog rows carry `source:"plugin"` + `plugin`.
- **Palettes and fonts are read through the plugin dir's `os.Root`** (`readThemePaletteFS`, `pluginBGRoot`), same as served files, so a symlink out of the plugin is refused. Backgrounds are served under the existing `/omarchy/bg/<id>/` route but `no-cache` (edited in place), and the plugin-bg map is an atomic rather than a field under `omarchyMu`, because `themeCatalog` lists backgrounds while holding that read lock.
- **`syncThemes` (from `noteIfChanged`) rebuilds only when the contributed set's digest moves** — enable, disable, re-approval, or the 10s rescan seeing a changed palette (`themeSig` hashes colors.toml/alacritty.toml/light.mode bytes and background names). A rebuild FORCES a `plugins_rev` bump even when the listing reads the same, since that bump is what makes browsers drop their theme-catalog cache. If the hub's current theme is a plugin theme whose def changed, it calls `setLocalHerdrTheme` (the generated `[theme.custom]` block in herdr's config holds the palette, so the file must be rewritten); otherwise it just nudges `refreshTheme`. A withdrawn current theme degrades like a theme only a newer binary knows (`Foreign`).
- **Fingerprint**: theme ids and fonts' id/family/category are in it, file contents and labels are not (a palette edit is not a permission change). Both are `omitempty` in the canonical JSON so every plugin approved before this keeps its fingerprint.
- **`ui_state.typography`** — `{sans, display, label, mono, terminal, chat}` → a font global id `plugin:<name>:<font>`. Merged PER SLOT (detached before the decode like the atmosphere collections, then `mergeTypography`), `""` deletes a slot (the default is the absence of a choice), unknown slot / malformed id → 400 and the whole patch is dropped. Well-formed ids for a disabled plugin are KEPT. The terminal slot keeps the Nerd Font as the fallback family so TUI icon glyphs still render. Font files are served by `/plugins/<name>/` with an explicit `font/*` Content-Type (Go's table has none, and nosniff would make a missing one fatal); only enabled plugins list `fonts[].faces`.
- **Chat styles and `ui_state.chat_text`** (`chattext.go`, `lib/chat-text.ts`). A manifest's `chat_styles` are numbers (size, weight, line_height, letter_spacing, width, backing) plus an optional `font` that must be one of the SAME plugin's fonts; `chatTextRanges` is the one range table for both a plugin style and a stored value, restated in `CHAT_TEXT_SPEC` and re-checked in the browser before anything is written into a `--chat-*` property. Not in the fingerprint (like a palette's colours). `ui_state.chat_text` is `{preset?, <field>?}` merged PER FIELD (null, or a `""` preset, deletes; detached before the decode like typography); each field resolves set > picked style (enabled plugins only) > `CHAT_TEXT_DEFAULTS`, and `applyChatText` pins every property on `<html>` defaults included, so `index.css` keeps no fallback numbers of its own. The rules are scoped to `.chat-text` (the single chat), never the agents grid's cards. The `chat` typography slot falls back to the picked style's font, then to `--font-sans`. `ui_state.terminal_text` (size, weight, line_height, letter_spacing; `terminalTextRanges`, no preset, no plugin styles) is the same per-field store via `textPrefKind`; `lib/terminal-text.ts` writes it into every xterm through `setTermTextOptions`, which shares `applyTermFont`'s per-terminal wiring (keyed on stack + metrics) and its resize nudge. It applies nothing until `uiStateSettled()`, so a terminal is not refit twice at boot, and with nothing set it equals ttyd's `-t fontSize=14` launch.
- **Install/link/update are ergonomics, never a grant** (`plugininstall.go`, modelled on herdr's `plugin install` and Luvus's `module install`). A GitHub install shallow-clones into `plugins/.staging/<token>/` (hidden, so neither the scanner nor `/plugins/` sees it) with `core.hooksPath=/dev/null`, `protocol.file.allow=never`, `protocol.ext.allow=never`, no submodules, `GIT_TERMINAL_PROMPT=0`, `GIT_LFS_SKIP_SMUDGE=1` and the minimal child env; deletes `.git`; caps the checkout at 50 MB / 5000 files; refuses a symlink in the plugin dir pointing outside it and a subdir reached through a symlink; then validates with the scanner's own loader (`loadPluginManifest(dir, "")` — an empty dirName skips the name==directory check, since a staged or linked manifest has no directory of its own name yet). Confirm re-reads the staged manifest and requires BOTH it and the client's fingerprint to equal the preview's (409 otherwise), `os.Rename`s into `plugins/<name>`, and **resets** the grant (a stale approval left under that name must not approve a new plugin) — approving the preview's fingerprint only when `enable`. Previews live in memory (`staged`), expire after 10 min, are swept on the rescan tick, and unowned staging dirs are removed at boot. `pluginCloneURL` + `pluginGitAllowFile` are the TEST seam (a local bare repo over `file://`); production never allows the file transport, and `TestPluginCloneRefusesFileProtocol` pins it.
- **Install records** are the `plugin_sources` settings key beside the grants: `{kind: github|linked, source, ref, commit, installed_at, updated_at?, path?}`; no record = `local` (hand-placed, everything that worked before). The listing's `source` object always has a `kind`. `pluginManager.scan()` is `scanPlugins` plus the linked records (a plugins/ directory of the same name shadows a link; a vanished link path is `invalid` with the reason). Only `github` may be uninstalled or updated, only `linked` unlinked; a `local` plugin is refused with "delete the directory yourself" (the Omarchy-uninstall stance). Uninstall re-checks that `plugins/<name>` is a direct child and not a symlink before `RemoveAll`, and drops record, approval and trust.
- **A directory swap holds the plugin** (`pluginManager.held`, `hold`/`unhold`): reconcile treats a held name as not wanted, so its server is stopped synchronously and a rescan tick landing mid-swap cannot restart it on a half-moved directory. Update moves the old dir aside into the stage, the new one in, and on failure moves the old one back (`pluginRename` is the seam the rollback test fails). The approval is not touched: an unchanged fingerprint stays enabled, a changed one reads `needs_approval` by the ordinary rule. `installMu` serializes every operation that moves directories or records.
- **Per-plugin data dir** `<lassoDir>/plugin-data/<name>` (0700, created by the server's `launch`, derived from the plugins dir's parent so tests stay in their temp dir): mounted rw at `/data` with `-e LASSO_PLUGIN_DATA=/data` in the sandbox, `LASSO_PLUGIN_DATA=<host path>` for a trusted child — both appended AFTER the manifest's env so it cannot be redirected. It survives uninstall unless `purge_data`.
- **Logs**: `GET /api/plugins/<name>/log` answers `{name, sandboxed, lines, note?}` from the manager's per-plugin `lineRing` (500 lines, kept across that plugin's restarts), sandboxed or trusted alike; the CLI's `-f` polls it every 2s.
- **`min_lasso_version` / `platforms`** are runtime checks in `validate` (`validateRuntime`): an older lasso or another OS makes the plugin `invalid` with the reason; a `-dev` or unparseable running version passes. Neither is in the fingerprint.
- Unit tests never touch isb: `TestMain` sets `LASSO_ISB=off` and re-execs the test binary as a fake stdio MCP server (`LASSO_TEST_FAKE_PLUGIN_MCP`), driven through the TRUSTED host runner (or `m.runner` returning it for any isolation) with the mode in the manifest's `env`; resolution is tested with fake `isb` scripts and the `isbServeCheck`/`isbMiseInstalls` seams.

## Messaging agents (`src/agentmsg.go`, `src/replyinbox.go`) → `docs/design/agent-messaging.md`

`send_agent`, `read_agent`, `wait_agent`, `get_replies` and `reply_message` let a caller with no herdr of its own (claude.ai on a phone) talk to any herdr agent on any host lasso drives, and let agents reach each other across machines. Every description tells Claude Code agents to prefer their own inter-agent messaging when it reaches the other side.

- **Delivery is a bracketed paste of the message, then one short typed line through herdr's `agent.prompt`.** Claude Code wraps a long paste in `<pasted_content>` and the model won't act on instructions inside it unless its user's own words ask; as a single paste the test agent answered on screen and declined to reply. Don't collapse it back into one paste.
- **Replies come back over tailcat**: one `tailcat serve <port>` child forwards that ONE port to a loopback listener (never `all`). Key under `<lassoDir>/tailcat/` with `--fixed-region` and the remembered loopback port keep a pending message's reply command valid across restarts; both are keyed on the listen port so dev and production lasso never share an address.
- **The address is a capability; the per-message token is the authority.** First line `lasso-reply <token>`, token stored only as a SHA-256 hash, 1 MiB cap. Replies are untrusted data for the sender, never acted on by lasso.
- `get_replies` is scoped to the sending credential's `ClientID`. The old `message_agent` queue stays gone; existing databases keep their unused `agent_messages` table, and nothing drops it.
