# Auth (`src/caller.go`, `src/allow.go`, `src/accessjwt.go`, `src/tailnet.go`, `src/localguard.go`, `src/accessgate.go`, `src/oauth.go`, `src/web/src/lib/auth-state.ts`)

lasso is a writable shell on every machine it reaches, so "who is calling" decides everything. The model in one line: **a front door proves who is calling, lasso checks that proof itself on a listener dedicated to that door, and `LASSO_ALLOW` decides who among the proven may in.** The loopback listener keeps the trust it has always had. User docs: `docs/security.md`, `docs/deployment/tailnet.md`, `docs/deployment/cloudflare.md`. Tests: `caller_test.go`, `localguard_test.go`.

The handler chain, outermost first: `withInternalCDP` → `withCaller` → `withLocalGuard` → `accessGate.wrap` → `withAuthExcept` (UI_AUTH) → the mux and its per-route gates (`withMCPAuth`, `withCDPAuth`, the browser-tool gate).

- **lasso verifies, it never logs in.** No password form, no session cookie of lasso's own, no login page. Cloudflare Access and the tailnet already authenticate the person, with whatever MFA, device posture and policy the operator set there; a login lasso ran would be one more credential store to attack and one more expiry to manage. lasso's job is to check the door's proof (a signature, or an answer from tailscaled), never to trust that a request "must have" come through. `UI_AUTH` and `MCP_OAUTH` remain for the local listener and for clients that carry a lasso token, and a caller a network listener verified (`edgeVerified`) satisfies both, the browser-tool gate and the deprecated header gate, so moving to a network listener needs no shared password. The SPA follows from this: `hostFetch` sends `X-Requested-With: XMLHttpRequest` on every request, which is Cloudflare's documented way to get a 401 instead of a redirect to a login page that `fetch` cannot follow; a 401 sets the signed-out state (`lib/auth-state.ts`), and the bar's **Sign in again** is a plain reload, which runs the door's own login in the window, inside an installed app too. The event stream needs nothing of its own: every reconnect starts with `api.active()`, which goes through `hostFetch`.
- **A listener's role is fixed at accept time and fails closed.** `roleListener` stamps the role on every connection and `ConnContext` (`withConnRole`) copies it into the request context, looking through TLS. Nothing at request time infers the role from headers or addresses. On the network roles (access, tailnet, serve) a request without the door's proof is 403 before any handler, so a hostname with no Access application, a second tunnel, or a stray proxy pointed at the port lets nobody in. The access and serve listeners must be loopback (startup refuses otherwise) because their proof means something only when the door is the one thing that can reach them, and `-listen-access` refuses to start without `LASSO_ACCESS_TEAM` and `LASSO_ACCESS_AUD`. The local role is everything else and keeps its trust, so an existing loopback setup, lasso's own CLI and local agents work unchanged; the roles are what keep the new listeners from inheriting that trust.
- **Access: verify the assertion, never the header.** `accessjwt.go` checks `Cf-Access-Jwt-Assertion`: RS256 only, issuer `https://<team>.cloudflareaccess.com`, `aud` one of `LASSO_ACCESS_AUD`, `exp`/`nbf` with a minute's leeway. Keys come from the team's `/cdn-cgi/access/certs`, cached an hour; an unknown `kid` triggers a refetch at most once a minute, so a flood of made-up key ids is not a flood of requests to Cloudflare. Cloudflare's own guidance is to validate the header, not the `CF_Authorization` cookie, which is not guaranteed to be passed. `Cf-Access-Authenticated-User-Email` is a plain header anyone off the edge can send, which is why the header gate (`-require-access-header`) is deprecated and verifies the assertion instead whenever the verifier is configured. An assertion with an email is a person; one with only `common_name` is a service token, named `service:<client id>`.
- **The access listener skips the Host check.** The verified assertion already proves the request came through Cloudflare for this application, which a rebinding page cannot fake, so the public hostname needs no `LASSO_HOSTNAMES` entry. Every other listener gets the full guard.
- **Only the socket peer counts on `-tailnet`.** The caller is tailscaled's whois of `r.RemoteAddr`, which must be in `100.64.0.0/10` or `fd7a:115c:a1e0::/48`. `X-Forwarded-For` and `Tailscale-User-Login` are never read on this listener: anything on the path could write them. A tagged node is its tags, never its owner's login, since a tagged server is not the person who tagged it. Whois answers are cached per peer address for a minute, failures for five seconds, at most 4096 entries. tailscaled is reached over its LocalAPI unix socket with plain `net/http` (no Tailscale Go module, so no dependency to audit), else the `tailscale` CLI, which is how the macOS app is reached. The certificate is tailscaled's for the node's MagicDNS name (`/localapi/v0/cert/<name>?type=pair`), reloaded daily, the old one kept serving when a renewal fails. On Linux a non-root lasso needs `tailscale set --operator` for the certificate.
- **`-listen-serve` trusts a header, so its port is dedicated.** `tailscale serve` strips a client's copy of `Tailscale-User-Login` and sets its own for an untagged source; Funnel and tagged sources carry none and are refused. The header is worth something only because nothing but `tailscale serve` reaches that loopback port. That is why it is a listener of its own and never the `-listen` port, where any local process could send the header.
- **`LASSO_ALLOW` decides among the proven, and its unset default is per door.** One list (`allow.go`) for every network listener; the local listener never reads it. Unset, the access listener admits whoever Access admitted (people everything, service tokens the machine paths), because an Access policy, Service Auth included, is an explicit operator grant. The tailnet and serve listeners admit only the node owner's login, because "anyone on the tailnet" includes users a device is shared with and every tagged device; a tagged node has no owner and admits nobody until listed. Set, it is the whole rule on every network listener: a person not listed is refused even if Access admitted them.
- **Self-credentialed paths skip the proof.** `/hooks/bots`, `/bot-channel` and `/talk` carry their own key (a job's webhook key, a bot's channel token, a bot's Talk key) and their senders have no identity to prove: a webhook service or a client's chat app reaches them through an Access Bypass policy, which strips the assertion. So `withCaller` passes them through on a network listener unproven, with no caller and their `Authorization` untouched, and nothing else on the listener is reachable that way.
- **Machines are kept off `/api`.** A machine caller (service token, tagged node) reaches only `machinePaths`: `/mcp`, `/herdr-mcp`, `/cdp`, the webhook, bot-channel and Talk paths, and the credential-less OAuth endpoints. `/api` is the UI's API and has no per-host checks (a tab names any host; the file endpoints read any path there), so an agent credential with it would reach every host's files and terminals, while the MCP surfaces are where host scope (`callerscope.go`) is enforced. The exits are deliberate and human-made: a `ui:` prefix on the `LASSO_ALLOW` entry, or a lasso token whose consent granted the `ui` scope. For the same reason a plain `mcp` token never satisfies `UI_AUTH`; `uiTokenOK` accepts only a token with `ui`, and only the consent screen grants it, with wording that says "its whole UI and API". `client_credentials` never grants it. With `MCP_OAUTH` set, an `/api` 401 adds a `Bearer` challenge (RFC 9728 resource metadata, scope `mcp ui`) beside `Basic`, which is how a native client such as the Mac app finds where to get one.
- **`X-Lasso-Token` exists because `Authorization` is sometimes taken.** Behind Access's Managed OAuth, a connector's `Authorization` carries Access's token. `normalizeLassoToken` moves `X-Lasso-Token` into `Authorization`, where every gate and the MCP SDK look, before anything reads it. On a network listener, a bearer lasso did not issue is **dropped, not refused**, so Access's token is never mistaken for a bad lasso one and the verified identity carries the request. A verified caller with no lasso token is unidentified for host scope (the fleet view, as on open `/mcp`); one with a lasso token gets that token's scope. That is why `MCP_OAUTH` and Managed OAuth coexist: OAuth routes 404 while `MCP_OAUTH` is unset, so nothing of lasso's competes with Access for a connector's discovery.
- **The local guard exists because the browser is the attacker's way in.** A loopback lasso trusts whoever connects, and a web page can reach it through the visitor's browser by two roads. DNS rebinding makes a page same-origin with lasso; only the `Host` header still names the attacker, so `hostGuard.allows` admits IP literals (a rebinding page cannot make the browser send an IP as its own Host), `localhost`/`*.localhost`, the `-listen` host, this machine's hostname (and short and `.local` forms), its tailnet names (`tailscale status`, best effort, two seconds), and `LASSO_HOSTNAMES`; anything else is 421 with a hint naming the variable. Cross-site requests (a form `POST`, a `text/plain` fetch, a websocket to `/terminal/`) skip CORS entirely, so an unsafe request (any method but GET/HEAD/OPTIONS, or a websocket upgrade) must carry an `Origin` matching its own `Host` (or `X-Forwarded-Host`, which a cross-site page cannot set without a preflight lasso never answers), or no `Origin` and a `Sec-Fetch-Site` of `same-origin`/`none`. Origin `null` never passes: plugin frames talk to lasso through `postMessage` only. Exempt: `/oauth/register` and `/oauth/token` (browser OAuth clients call them from their own origin) and `/hooks/bots`, `/bot-channel` and `/talk` (their own credentials). Agents, the CLI and curl send neither header and are untouched. It runs on every listener ahead of every credential, which is why the MCP SDK's own loopback-only `Host` check is disabled (`DisableLocalhostProtection`) and the Vite dev proxy keeps the browser's `Host` (`changeOrigin: false`). A refusal is logged with the host and `Origin` only, never the query string or another header.
- **A machine lasso drives is never a client of lasso.** Never forward lasso's port onto a host lasso manages (an `ssh -R`, a tunnel, a socat): there, every agent lasso runs and every other process would reach the local listener's trust, and lasso has no way to tell them from the human on lasso's machine. An agent on another machine comes in through a network listener as a machine, with a service token or a tag, plus a per-host lasso token for scope. The tailnet policy is the outer wall: a box with no business reaching lasso should be unable to open a connection to it at all; `LASSO_ALLOW` and tokens are the walls inside.
- **Deprecated, still working:** `-insecure-no-auth` (a bare non-loopback `-listen`: plain HTTP, everyone on the network in, no identity) and the header-only Access gate (`-require-access-header` without `LASSO_ACCESS_AUD`). Both stay so an existing deployment keeps starting; neither is the way to set up a new one.
