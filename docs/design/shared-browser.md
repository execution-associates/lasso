# Browser tab and the shared browser (`src/web/src/components/BrowserTab.tsx`, `LiveBrowser.tsx`, `src/web/src/lib/cdp.ts`, `src/web/src/lib/browser-url.ts`, `src/browser.go`, `src/browserprofiles.go`, `src/cdpproxy.go`, `src/mcp_browser.go`, `src/mcp_browser_profiles.go`, `src/browsermcp.go`)

Two modes behind one toolbar switch, stored as `ui_state.browser_mode` (`live` | `embed`, default `live`; validated on write, an unknown stored value reads as `live` — `normalizeBrowserMode`). **Live** (labelled **Agent** in the UI, and **Embed** is labelled **Iframe**: the stored values kept their names, the labels say who else sees the page) is a headless Chromium lasso supervises on its own machine, drawn in the tab from a CDP screencast with input forwarded; agents drive the same Chromium over `/cdp`. **Embed** is the iframe the tab always was. The stored preference is not always what is shown: with `GET /api/browser` answering `available:false` (or failing — an older server) the tab shows Embed with a line giving the reason, **without** rewriting the preference, so installing Chromium later brings Live back on its own.

### Embed (unchanged)

A URL bar and an iframe. A bare port (`5173`, `:5173`, `localhost:5173`) resolves to `http://<location.hostname>:<port>`; a schemeless URL gets `https://` except for a loopback host, which gets `http://` (`normalize` in `lib/browser-url.ts`). There is no backend behind the frame: no `/api/preview`, no `tailscale serve` forwards, no Cloudflare wildcard demux (`lasso devproxy`), no Access-cookie priming. All of that existed and was **deliberately removed** — it was a lot of per-deployment wiring (DNS wildcard, tunnel ingress, an Access app, a supervised daemon, a `-preview-public-domain` flag) to work around a browser rule, and the rule wins anyway.

- **What the browser allows is the whole contract.** An HTTPS origin can't frame an `http://` dev server (mixed content) and a public origin can't frame a private/tailnet one (Private Network Access). Both cases are detected and reported in the tab, with open-in-new-tab as the out. Don't reintroduce a tunnel to dodge them.
- `probeReachable` (a `no-cors` fetch), not the iframe's `onLoad`, is the failure signal: a PNA-blocked frame still fires `onLoad` while rendering blank.
- **A site that forbids framing is the one thing the browser can't tell the page** (`src/frameable.go`, `GET /api/frameable`). `X-Frame-Options` and CSP `frame-ancestors` refuse the embed silently — `onLoad` fires, the no-cors probe succeeds, the frame is blank — and both headers are unreadable cross-origin. So lasso fetches the URL server-side and applies the browser's rules for the tab's origin. It is **advisory, not a proxy**: nothing is served through it, only a boolean comes back, and any fetch failure answers `null` and the tab says nothing, since lasso's machine is not necessarily where the browser reaches the page from.

### Live: the shared browser

**It is not the preview tunnel coming back.** That tunnel served the *user's* browser a page from somewhere it could not reach; the shared browser is a whole browser running on lasso's machine, and what crosses the wire is CDP — a screencast out, input events in. Nothing is framed, so none of Embed's three limits apply (mixed content, PNA, `frame-ancestors`), and there is no per-deployment wiring: `/cdp` rides whatever already fronts lasso. The flip side is that it browses **from lasso's machine**: a bare port in Live resolves to `http://localhost:<port>` there (`resolveLive`), and `about:`/`data:`/`file:`/`chrome:` URLs pass through literally instead of growing an `https://`.

- **No Go websocket library, on purpose.** `go.mod` has none and gains none. The Go side is a process supervisor (`browser.go`) plus a reverse proxy (`cdpproxy.go`): `httputil.ReverseProxy` already carries websocket upgrades — it is how `/terminal/` reaches ttyd — so lasso never parses a CDP frame. The Browser tab is **just another CDP client** (`lib/cdp.ts`, the page's native `WebSocket`), a peer of the agents on the same endpoint. That is also why the tab never assumes it is alone: its page list is `Target.setDiscoverTargets`, not a list it keeps. **It shows a tab strip of the selected browser's pages and follows the newest**: a `targetCreated` for a page after discovery has started selects it (the existing pages are announced as `targetCreated` too when discovery begins, hence the `discovered` flag), so an agent opening a page puts the human on it. A closed page falls back to another open one. The strip is what makes several pages per browser usable: without it, a second page would be one nobody could reach.
- **One socket, to the browser target.** Pages are reached with flat sessions (`Target.attachToTarget` + `flatten:true`), so switching tabs is a detach/attach on the same connection. The screencast is `Page.startScreencast` sized to the canvas × devicePixelRatio, every frame acked; the viewport follows the panel via `Browser.setWindowBounds` (falling back to `Emulation.setDeviceMetricsOverride`). Input maps canvas → page CSS px through the last frame's metadata; ⌘K/⌘I/⌘\ and lasso's other shell chords are left to bubble, editing chords go out carrying the editor command (the platform's key bindings are not consulted for synthetic input), paste goes out as `Input.insertText`. `cdpURL` addresses lasso's **origin**, never the tab's host — there is one shared browser per lasso, whatever host a tab is driving.
- **It streams only while someone can see it.** `BrowserTab` gets `active` from App.tsx (Browser selected and the sidebar open) and Live also watches `document.visibilityState`; inactive, it stops the screencast and **closes the socket**, which is what lets the idle stop fire. On reveal it calls `POST /api/browser {action:"start"}` first if the status says stopped, then reconnects with backoff (`reconnectDelay`, 1s→15s) — the same path that rides out a browser restart.
- **Lazy start, idle stop, and how "idle" is counted.** Chromium launches on the first `/cdp` request (a `browser_*` tool's child dialing in is one), `POST /api/browser {action:"start"}`, or the `shared_browser` tool; `run()` stops it after `-browser-idle` (`LASSO_BROWSER_IDLE`, 15m, `0` = never). A proxied websocket holds `ServeHTTP` for the connection's whole life, so an in-flight counter bracketing `serveCDP` (`begin`/`end`) **is** the live-client count — no websocket bookkeeping needed. The reaper re-checks under the launch semaphore so a client connecting between the look and the stop wins.
- **The endpoint comes from `DevToolsActivePort`, not a fixed port.** `--remote-debugging-port=0` lets the kernel pick (9222 would collide with a second lasso or a Playwright run); Chromium writes `<profile>/DevToolsActivePort` (port, then `/devtools/browser/<id>`) once the socket is bound, which makes the file both the readiness signal and the port. The stale file is deleted before each launch and polled for ≤15s (`browserPortWait`); a process that exits first fails with its stderr summarized — the `:FATAL:` line, not the tail, which is a register dump.
- **`/cdp` is the stable address.** Chromium's browser id changes every launch; bare `/cdp` maps to whatever it is now, `/cdp/devtools/...` and `/cdp/json/...` pass through, and every websocket URL in a `/json` answer is rewritten back through `/cdp` (`ws`/`wss` from `r.TLS` or `X-Forwarded-Proto`, **not** "non-loopback means https" — lasso is routinely plain http on a tailnet). An agent configured once with `--wsEndpoint ws://<lasso>/cdp` survives idle stops and restarts. The outbound transport pools by `127.0.0.1:<port>`, unique per launch, so a relaunch can never be served down the old instance's connection.
- **Outbound headers, and why each is touched.** `Host` is rewritten to `127.0.0.1:<port>` — Chromium answers only an IP or `localhost` Host (its DNS-rebinding guard). `Origin` is **deleted** — Chromium ≥111 refuses a websocket whose Origin is not in `--remote-allow-origins`. `Authorization` and `Cookie` are dropped (lasso's credentials are not Chromium's), and `Accept-Encoding` on `/json` so the body can be rewritten.
- **The Origin guard must run before the strip, and it is not optional** (`cdpOriginAllowed`). Deleting Origin switches off Chromium's own cross-site defense, so lasso has to do its job first: any page a user visits may open a websocket to a loopback lasso, and without this it could read, type into and navigate the shared browser. No Origin passes (a CLI/agent client); an Origin passes only when its host:port equals the request's `Host`, or `X-Forwarded-Host` when a front proxy set one (default ports normalized); anything else, `null` included, is 403. Tested — keep it that way.
- **The gate** (`withCDPAuth`): `/cdp` is in `withAuthExcept`'s exempt list like `/mcp`, because its clients are agents carrying a token rather than a browser holding UI_AUTH, and it applies its own rule. `MCP_OAUTH` set → what `/mcp` accepts (lasso bearer token or UI_AUTH basic), and a token's scope must `allows("local")` (`cdpScopeCheck` — otherwise a credential the tool refuses could skip the tool and dial `/cdp` directly); plus, **with UI_AUTH unset**, a same-origin browser request (the Browser tab, which cannot mint a token) passes without one — that configuration already leaves `/terminal/` open to anyone who reaches lasso, and the Origin guard has already refused every other page. Only `UI_AUTH` → basic, which a browser sends on its websocket too, as `/terminal/` relies on. Neither → open, `/mcp`'s trust model. `gate.wrap` (Access) fronts all of it, unchanged.
- **Sharpness is a LAUNCH flag, because the screencast ignores everything else** (`-browser-scale`/`LASSO_BROWSER_SCALE`, default 2 → `--force-device-scale-factor`). `Page.startScreencast` always delivers frames at the page's CSS size: an `Emulation.setDeviceMetricsOverride` scale factor makes the page *render* at 2x (`devicePixelRatio` reads 2) and the frames still arrive at 1x — measured 474x585 for a 474x585 viewport, with or without `maxWidth`, jpeg or png. `Page.captureScreenshot` does honor the override, but it repaints, and a repaint emits screencast frames (measured: two per screenshot), so "sharpen after the stream goes quiet" becomes a loop that flashes between the two images and eats the CPU. Only a scale set at launch reaches the frames (measured 2560x1426 for 1280x713). Layout stays in CSS px for everyone; the cost is raster CPU and 4x-pixel agent screenshots, which is why it is a knob.
- **Headless's window is NOT its viewport.** `--headless=new` keeps 87px of invisible window chrome, so a window sized to the tab's box leaves the page short and the frame letterboxed. `LiveBrowser.fit` reads the gap as `outerHeight - innerHeight` (one snapshot, so it is right at any window size) and sizes the window to the box plus that gap. Two traps it avoids: resizing and then re-reading `innerHeight` answers before the resize lands, i.e. with the PREVIOUS size, which reads as "already correct"; and the gap is kept at module level (`chromeGap`), because a component ref resets on every Live → Embed → Live round trip.
- **The resource cap, and the dbus escape it needed.** Headless Chromium on a GPU-less box software-rasterizes and will take several cores. On linux with `systemd-run` on PATH **and** `XDG_RUNTIME_DIR` set (how `--user` finds the manager — absent under a bare ssh session or a container), it launches as `systemd-run --user --scope --quiet --collect -p CPUQuota=… -p MemoryHigh=… -- env DBUS_SESSION_BUS_ADDRESS=disabled: <chrome> …` (`-browser-cpu`/`LASSO_BROWSER_CPU` 200%, `-browser-mem`/`LASSO_BROWSER_MEM` 2G; `off` or empty lifts one, both off = no scope). `--scope` execs in place, so the pid lasso holds is Chromium's and the process-group kill and `Pdeathsig` still reach it. **The `env DBUS_SESSION_BUS_ADDRESS=disabled:` is load-bearing:** given a session bus, Chromium's browser process moves itself into an `app-org.chromium.Chromium-<pid>.scope` of its own (for the XDG portal) — an uncapped one, taking every process it launches afterwards out from under the quota; measured, only the zygote-forked renderers stayed capped. It is set only inside the scope, because systemd-run itself needs the bus. A capped launch that fails retries once uncapped (an uncapped browser beats none); `status().capped` says which happened.
- **Lifecycle backstops.** Own process group (`Setpgid`) so a stop takes renderers and zygote with it (SIGTERM, SIGKILL after 3s); `Pdeathsig: SIGTERM` on linux so a `kill -9` of lasso does not leave a browser burning cores; the shutdown path stops it synchronously after in-flight requests drain. `browserEnv` strips `UI_AUTH`, `MCP_OAUTH` and `LASSO_MCP_TOKEN` from its environment — any exploited renderer's `/proc/<pid>/environ` would otherwise hold them.
- **The data directory** (Chromium's profile) is `<lassoDir()>/browser-profile` (`LASSO_DIR`-aware). Cookies and logins persist; **open tabs do not** — `Default/Sessions` is deleted before every launch, because Chromium otherwise restores the last run's tabs on top of its `about:blank`, leaving one more blank tab per launch. So an idle stop closes the tabs, which is what "nobody is using it" means. Everything logged into this profile is reachable by every client that can reach `/cdp`.
- **A second lasso sharing the data dir is refused, not killed** (`reclaimProfile`). Chromium's `SingletonLock` would make a second launch hand its URL to the first and exit (reading as a crash), so lasso keeps `lasso-browser.pid` in the profile: Chromium's pid, then the owning lasso's. A live Chromium (cmdline naming this profile — `/proc`, or `ps` on a Mac) whose lasso is gone is an orphan and is stopped; one whose lasso is alive belongs to another instance (a dev build beside prod) and the launch fails naming `LASSO_DIR` as the fix, rather than pulling a browser out from under that instance's agents.
- **Binary resolution** (`resolveBrowserBinary`, first hit wins; the search space is a struct so tests fake it): `-browser`/`LASSO_BROWSER` (a path must exist, a name must be on PATH — an explicit choice that fails is **reported**, never silently replaced; `off` disables the feature); PATH `chromium`, `chromium-browser`, `google-chrome-stable`, `google-chrome`, `chrome`; the newest `~/.cache/ms-playwright/chromium-<build>/chrome-linux*/chrome` by **numeric** build; on darwin the Chrome and Chromium app bundles.
- **`No usable sandbox!` is named, not worked around.** Ubuntu 23.10+ (`kernel.apparmor_restrict_unprivileged_userns=1`) lets only binaries with an AppArmor profile create the user namespaces Chromium's sandbox needs; Playwright's and hand-unpacked builds have none. `launchFailure` recognizes it and says what to do — a packaged Chrome/Chromium (Ubuntu ships profiles for those paths), an AppArmor profile granting `userns`, or knowingly `LASSO_BROWSER_ARGS=--no-sandbox`. Adding `--no-sandbox` automatically would quietly run every page an agent opens with lasso's full privileges; it is added only as root, where Chromium refuses to start without it.
- **It does not announce itself as a bot.** Headless Chrome sends `HeadlessChrome/<v>` in its user agent and reads `navigator.webdriver === true`, and bot checks (Cloudflare Turnstile) refuse that browser outright — including for the human clicking "I'm human" by hand in the Browser tab. So every launch gets `--disable-blink-features=AutomationControlled` and `--user-agent=` the UA a headed Chrome of the SAME version sends (`browserUserAgent`: `<bin> --version`, reduced form `Chrome/<major>.0.0.0`, cached per binary; skipped when `LASSO_BROWSER_ARGS` sets its own). The client-hint brands already read Chromium/Google Chrome. CDP is unaffected.
- **`/api/browser*` are ordinary UI routes** behind UI_AUTH (status, start/stop/restart, the browser list). Settings and the tab share one React Query entry (`qk.browser`), so a start in one shows in the other.
- **`shared_browser` MCP tool** (`mcp_browser.go`; `lasso mcp shared-browser` for free). It does not drive a browser — the `browser_*` tools and CDP clients do that — it starts one (`browser` picks which; `start` defaults true; it `touch()`es first so the idle reaper cannot race the agent about to connect) and answers its raw CDP endpoints (`ws_endpoint`, `ws_path`, `http_endpoint`), `browsers_url` (the `/cdp/browsers` listing), `browser_tools`/`browser_tools_reason` (whether this server's `browser_*` tools can run, and why not), `pages` and `note`, refusing a caller whose reach excludes `local`. The go-sdk hands a tool the request's headers but not its `Host`, so `withRequestBase` stamps `X-Lasso-Request-Base` onto every `/mcp` request — **`Set`, not `Add`**, so a client cannot supply its own and steer where an agent is told to connect. The description carries the etiquette (open your own tab, don't navigate or close others', close yours, `localhost` is lasso's machine) because it is what the model reads; `/mcp`'s instructions carry it too.

### Browsers (`src/browserprofiles.go`, `src/mcp_browser_profiles.go`)

lasso can run several browsers, each with its own persistent cookies and logins. The human picks one at the bottom of the Browser tab (Agent mode); agents manage them over `/mcp`. **Everything a human or an agent reads calls them browsers** — the tools, their arguments, the Browser tab's bar ("Browser") and dialog ("Browsers"), the docs. The code and storage call one a *profile* (`browserProfile`, `settings.browser_profiles`, `/api/browser/profiles`, the `browser-open` event's `profile`), because that is how existing data is keyed: renaming the storage would need a migration and buys nothing a reader sees. Keep the two vocabularies where they are.

- **A browser is its own Chromium PROCESS, not a browser context.** `Target.createBrowserContext` contexts are incognito-like: their cookies, localStorage and IndexedDB die with them — exactly what a browser here must not do. A user-data-dir per browser is the one thing that persists all of it. Everything above (lazy start, idle stop, the systemd cap, the pid-file reclaim, `Default/Sessions` deletion) is per `browserManager`, and there is one manager per browser that has been used. The cost: each RUNNING browser is a Chromium under its own cap (`-browser-cpu` each, not shared); an unused one costs nothing, and each idle-stops on its own. `browserFleet.run` is the one ticker that reaps them all.
- **The default browser** is `<lassoDir>/browser-profile`, bare `/cdp`, `sharedBrowser`, and what every tool uses when `browser` is omitted. The others are one JSON list in `settings.browser_profiles` (`id`, `name`, `cdp_url`, `created_at`), with their directories at `<lassoDir>/browser-profiles/<id>`; the default's display name, if renamed, is `settings.browser_default_profile_name`. It cannot be deleted.
- **Ids** are `^[a-z0-9][a-z0-9-]{0,31}$` — a path segment in a URL and a directory name, so nothing that means anything else in either — derived from the name when not given (made unique with `-2`…), and unique names are enforced case-insensitively. Anything that takes a browser (the tools' `browser`, `POST /api/browser`'s `profile`) accepts an id or a display name (`resolveProfile`); an unknown one is an error that lists the real ones (`no browser "x"; browsers: …`). At most 32 browsers.
- **Addresses**: `/cdp/p/<id>` (browser target), `/cdp/p/<id>/devtools/…`, `/cdp/p/<id>/json/…`, with `/json` websocket URLs rewritten back through the same prefix (`rewriteCDPJSONAt`) — a rewrite to bare `/cdp` would silently hand a client the default browser. `serveCDPRouted` runs the Origin guard before it looks the browser up. A browser's stop closes only ITS `browser_*` children (`browserStoppedFor`); the opt-in cap on children is global.
- **`GET /cdp/browsers` is lasso's own listing on the CDP surface**, not a passthrough: the list of browsers is the one thing a CDP-only client (Playwright, curl) cannot discover from a single browser's `/json`, and `list_browsers` lives on `/mcp`, which such a client does not speak. It answers `{"browsers": [...]}`, every browser (default first) with `id`, `name`, `default`, `running`, `started_at`, the running browser's `tabs`, and the address to connect to it — `ws_path`/`ws_url` and `http_path`/`http_url` (`/cdp` or `/cdp/p/<id>`, absolute since the caller's Host is known). `/cdp/profiles` answers the same list under a `profiles` key, for clients that ask by that name (`cdpListingRequest`). Both are served under every prefix (`/cdp/browsers`, `/cdp/p/<id>/browsers` alike — the listing is lasso's, not one browser's), run after the Origin guard and behind `withCDPAuth` like all of `/cdp`, and **never start a browser**: one that has never run is listed stopped, no manager created. `shared_browser` returns the URL as `browsers_url`. The `/cdp/p/<id>` prefix keeps its `p`: it is a raw CDP address other tools are configured with.
- **Delete** retires the manager first (`retired`: a request still holding it cannot relaunch into the directory), stops it, drops it from the list, then removes the directory — every login in it. A new browser that reuses a deleted id starts with its directory wiped, so it never inherits a predecessor's logins.
- **HTTP**: `GET /api/browser` keeps its top-level fields as the default browser's, adds `tools_available`/`tools_binary`/`tools_reason`/`tools_sessions` (the `browser_*` tools: can they run, which chrome-devtools-mcp, why not, how many MCP sessions hold a child) and `profiles` (each: `id name cdp_url default running started_at capped reason pages ws_path`). `POST /api/browser {action, profile?}`, `GET|POST /api/browser/profiles`, `GET|PATCH|DELETE /api/browser/profiles/<id>` (400 plain text for input, 404 unknown). Ordinary UI routes behind UI_AUTH, named for the storage. Every change broadcasts a `browser-profiles` SSE event so other lasso tabs refetch the list.
- **MCP tools**: `list_browsers`, `create_browser`, `update_browser`, `delete_browser`, `list_browser_tabs`, `open_browser_tab`, `show_browser_tab`, `close_browser_tab`, and `shared_browser` — every one naming its browser with `browser`. All refuse a caller whose reach excludes `local` (`requireLocalBrowser`). They manage WHICH browsers and pages exist and which page the human sees; driving a page is the `browser_*` tools' job. Each browser's `ws_endpoint` is per browser; there is no per-browser MCP address, on purpose: the `browser_*` tools on the one server reach every browser by argument, so a browser created mid-task needs no config edit and no reconnect. Tabs are opened with `PUT /json/new` and closed with `/json/close/<id>`, ids checked against `^[A-Za-z0-9_-]{1,64}$` before they go into a path. `open_browser_tab` accepts only http(s) and `about:blank` (a bare host gets `https://`, `http://` for loopback) — `file:`/`chrome:`/`javascript:` are not pages to show a human.
- **`browser-open` is `open_file` for tabs.** `open_browser_tab` (unless `show:false`) and `show_browser_tab` push `{profile, tab_id, url, from}` to every connected tab, and report `delivered` honestly (0 = nobody saw it; the tab is still open in the browser). Only a VISIBLE lasso tab acts: it reveals the Browser tab, forces Agent mode for that client without rewriting `ui_state.browser_mode`, switches to the browser, and selects the tab once discovery reports it (a wanted-but-not-yet-discovered target must not be clobbered by the fall-back-to-the-first-page rule).

### Remote browsers (`src/browserremote.go`)

A browser with a `cdp_url` is one lasso DIALS instead of launching: a Chromium already running somewhere else (another machine on the tailnet, a container, behind a tunnel), reached at its DevTools HTTP base, `http://host:port` or `https://host[:port]`. **lasso is agnostic about it**: how that browser is started, kept alive, where its traffic goes and how it is secured is up to whoever runs it (lasso configures no proxy for any browser, launched or remote: that is the browser's own business). All lasso needs is the standard remote-debugging endpoint (`/json/version`, `/json/list`, `/json/new`, `/json/close`, the `/devtools/` websockets), and everything above that (`/cdp/p/<id>`, the `browser_*` tools' children, the Browser tab's screencast and input, the tab tools) is the same code a launched browser runs through. The one seam is the address: `browserProc.target()` is the remote `host:port`, `urlScheme()` its scheme, `hostHeader()` what it is sent.

- **Why dial, not attach.** A connector next to the browser dialing in to lasso would work behind NAT and keep the debugging port on loopback, but it is a protocol and a credential lasso would own. Dialing an address makes the connection the operator's problem, solved with whatever they already use (tailnet, ssh `-L`, a tunnel), and keeps lasso to one rule: give it a CDP address.
- **Nothing to launch, nothing to stop.** `ensure` on a remote browser is `ensureRemote`: read `/json/version`, take its browser websocket path: `/devtools/browser/<id>`, or a bare `/devtools/browser` (`isBrowserWSPath`). A stop, an idle stop and shutdown only DETACH (the proc is dropped and `onStop` fires so the `browser_*` children close); the remote browser is never signalled. No pid file, no `Default/Sessions` deletion, no systemd cap, no launch flags (`--force-device-scale-factor` sharpness and the UA override are the remote side's business).
- **It restarts on its own schedule.** Its identity is trusted for `remoteCheckEvery` (2s); the next `/cdp` request after that re-reads `/json/version`. A new browser id is a restart and one that stops answering is a stop (an id-less path cannot show a restart, only a stop): either fires `onStop`, exactly like a launched browser's exit, so each session's child for that browser reconnects to whatever is there now. Bare `/cdp/p/<id>` is rewritten to the browser's current id on every request, as for a launched browser, so clients never hold the remote id.
- **The Host header.** Chromium's DevTools server answers only a Host that is an IP or `localhost`, so plain `http` to a host NAME goes out as `localhost:<port>` (`cdpHostHeader`); over `https` the name is kept, since what answers there is something in front of Chromium that routes by it. The remote address never reaches a client: `/json` answers are rewritten through `/cdp/p/<id>` by path, as always.
- **Id-less browser targets** ([Kitesurf](https://kitesurf.dev), a stateless CDP service). Its `/json/version` answers `webSocketDebuggerUrl: wss://kitesurf.dev/devtools/browser` with no `/<id>`, so `dialRemoteBrowser` accepts exactly `/devtools/browser` as well as `/devtools/browser/<id>` (anything else is still refused) and `cdpPublicPathAt` maps both to the bare prefix. It needs its name in the Host header, which `https` keeps. It lists one page and answers `PUT /json/new` and `/json/close` with 404, so `open_browser_tab`/`close_browser_tab` fail on it with an error saying so (`devtoolsNotFound`); drive its page through the `browser_*` tools or CDP.
- **The default browser can be remote too.** Its `cdp_url` lives in `settings.browser_default_cdp_url`, so bare `/cdp` and the `browser_*` tools without `browser` reach the remote browser. `GET /api/browser` then reads `available` with no Chromium on lasso's machine.
- **Validation** (`validateCDPURL`): `http`/`https` only, no credentials (lasso sends none), no path, query or fragment (lasso adds the paths); a `ws://…/devtools/browser/…` URL is refused with the HTTP base it should have been. Endpoints that are ONLY a websocket (hosted browsers handing out `wss://…?token=`) have no `/json` and are not supported: the tab list, `open_browser_tab` and the Browser tab's page discovery all read `/json`.
- **Trust.** Whatever is logged in to the remote browser is reachable by every client that can reach `/cdp/p/<id>`, under the same gate as a launched browser. Creating one requires `local` reach, like every browser tool, and lasso will dial whatever address it is given.
- **HTTP/MCP**: `cdp_url` on `POST /api/browser/profiles`, `PATCH /api/browser/profiles/<id>`, `create_browser`, `update_browser`, and in every browser status. The Settings dialog does not edit it.

### The browser tools on `/mcp` (`src/browsermcp.go`)

Google's chrome-devtools-mcp drives lasso's browsers as tools on lasso's OWN MCP server, beside `list_agents` and the rest: an agent that has lasso's `/mcp` has the browser, with nothing installed on its machine, nothing more to add to its config, and lasso's auth in front. `GET /api/browser` reports `tools_available`/`tools_binary`/`tools_reason`/`tools_sessions` (sessions holding at least one child — agents actually browsing, not every client connected); Settings shows `/mcp`'s URL, the add command and that count.

- **Names: `browser_<name>`.** chrome-devtools-mcp's `click` is `browser_click`, `navigate_page` is `browser_navigate_page`, `take_screenshot` is `browser_take_screenshot`. The server has many other tools, and a bare `click` or `list_pages` beside `list_agents` reads as nobody's; the prefix says whose. lasso's own browser tools (`list_browsers`, `open_browser_tab`, …) do not start with `browser_`, so the prefix is exactly the mark of a chrome-devtools-mcp tool. Its descriptions name sibling tools (`take_snapshot`, `list_pages`), so those mentions are renamed to match (`browserTool`, in the description and every `description` in the input schema) — only names with an underscore, because `click` and `fill` are English words as often as tools. The cached tool is never modified; registration works on copies.
- **Why a bridge.** chrome-devtools-mcp is stdio-only — no HTTP server mode — so lasso runs it as a child and speaks MCP to it with the go-sdk already in `go.mod` (`mcp.CommandTransport` + `mcp.NewClient`). Each child tool is mirrored onto the shared server (`sharedMCPServer`, the one `newMCPHandler` builds, which `attach` hands the bridge) with the low-level `Server.AddTool`; its handler forwards the child's own tool name + raw arguments (minus `browser`) and returns the child's `*CallToolResult` untouched, so image content (screenshots), `structuredContent`, `isError` and `_meta` pass through as chrome-devtools-mcp produced them. Pagination of the child's `tools/list` is followed. A tool whose input schema is not an object is skipped with a log line rather than handed to `AddTool`, which panics on one.
- **One `browser` argument for every browser, because an MCP server per browser is untenable.** Every mirrored tool gains an optional `browser` string (id or display name, as `list_browsers` shows them; omitted or `""` = the default). The bridge strips it and forwards to the session's child for THAT browser (`browserRoute`, `child`). It is resolved when the call runs (`resolveProfile`), so a browser created after the session started works without reconnecting and a deleted one is refused. **An unknown browser is a tool error (`isError`) listing the current ones — never a fallback to another browser**, which would act in the wrong browser with the wrong logins; a non-string `browser` is refused the same way. A tool that ever ships a `browser` argument of its own is passed through untouched (and logged) rather than hijacked. The argument's description names `list_browsers` rather than listing browsers: the schema is one per server, and a list in it would be stale the moment one is created.
- **One child per SESSION per BROWSER, on a server shared by every session.** chrome-devtools-mcp keeps per-client state — the selected page its page-scoped tools act on, console/network buffers, emulation — so two agents behind one child would steer each other's page; and one child dials one browser, so each browser a session uses needs its own. The shared server has one tool list for everyone, but every call carries its `*mcp.ServerSession`, and that is the key: `browserMCPBridge.live` maps a session to its `browserMCPSession`, made on its first browser call (`sessionFor`), whose `children` hold a slot per browser. Concurrent calls for one browser share one spawn (the slot's `ready`), the spawn runs detached from the calling request (a call that gives up still leaves the child ready for the next), and a failed spawn is forgotten so the next call retries. A spawn failure is that call's tool error (`isError`, binary missing, `exited during startup (exit status N)` with the tail of its stderr, or a handshake timeout); the session is unaffected. **A `pageId` belongs to one browser's child**, which the `pageId` description says: page ids from `browser_list_pages` in `work` mean nothing to the default browser's child, so an agent keeps passing the same `browser` for a page.
- **The session's end, and the idle stop that stands in for a session timeout.** A session's children end when the session does: `sessionFor` starts a watcher on `ServerSession.Wait`, which returns on DELETE or a server-side close. `/mcp` sets no `SessionTimeout` — its sessions are the long-lived orchestration connection every agent holds — so a client that vanishes without a DELETE leaves its session open, and its children would live forever. So `browserMCPBridge.run` (a one-minute ticker) stops the children of any session with no browser call in flight and none for `browserMCPIdle` (30m) (`reapIdle`); the session's entry stays, and its next call spawns afresh, as after a browser restart. At shutdown `closeAll` stops every child (right after `draining`, before `srv.Shutdown`, so a call waiting on a child answers and lasso never exits ahead of one); the `/mcp` sessions themselves are the server's to close.
- **Lazy: initialize and tools/list spawn nothing per session.** A child is ~175 MB RSS plus idle CPU (measured on titan), and every Claude Code session on a box loads lasso's MCP server at startup, so a child per session at connect would be a node process per agent whether it browses or not. The tool list comes from a **per-process cache** (`toolList`), learned by a short **probe child** (spawn, `tools/list`, close — about a second): once at startup, right after the listener is bound (`ensureTools` from main), and again on any `/mcp` initialize that finds the cache was learned from a different binary. The initialize waits up to `browserMCPListWait` (10s) for a probe in flight; one that takes longer still lands, and registering its tools sends every session `tools/list_changed`. The probe starts no Chromium: chrome-devtools-mcp dials CDP only when a tool runs (measured on 1.10.1 with an unreachable `--wsEndpoint`: `tools/list` answers all 30 tools). It is not counted against the cap.
- **A missing or broken chrome-devtools-mcp is never `/mcp`'s problem.** No binary, `LASSO_BROWSER_MCP=off`, or a probe that fails: `/mcp` initializes as always, with no `browser_*` tools, and `shared_browser` says why (`browser_tools_reason`). A failed probe is remembered per binary for `browserMCPProbeRetry` (1m), so a broken install is not re-spawned on every initialize. Each initialize re-resolves the binary (a PATH lookup and a stat — cheap), so installing chrome-devtools-mcp later adds the tools on the next initialize, and removing it withdraws them (`register(nil)`), both announced with `tools/list_changed`.
- **Binary upgrades.** The cache is keyed by the binary's resolved path (symlinks followed — a mise install dir names the version), size and mtime (`browserMCPBinKey`), so an upgrade in place is probed again by the next initialize. A shim whose target moves without the shim changing is invisible to that key, so every real spawn also re-lists and replaces the cache when the list differs (`learnTools`, logged), and re-registers the tools on `/mcp`. `register` compares by slice identity — `learnTools` hands back the cached slice itself when nothing changed — so an unchanged list touches nothing and sends no `list_changed`.
- **The cap is opt-in** (`-browser-mcp-max`/`LASSO_BROWSER_MCP_MAX`, default `0` = no limit). With children lazy, the processes that exist are the ones agents are using, and refusing one of them is worse than running it. When set, it counts live children plus spawns in flight (a reserved slot, so a burst cannot overshoot) across every session and browser, and a spawn over it fails that tool call with an error naming the knob and `0 = no limit`; connecting never does.
- **Lifecycle.** A browser stopping (`browserManager.onStop` → `browserStoppedFor`: a stop, an idle stop, a remote browser restarting, a crash) **closes only that browser's child in each session**; the sessions, and their children for other browsers, carry on, and the next call to that browser spawns a child that dials the new browser (and gets new page ids). The set is taken synchronously in the hook — a child that connects after this moment is on the next browser and must survive — and stopped in the background, because the hook runs with the launch semaphore held. A spawn still in flight is left alone: it has not dialed CDP yet and will reach the next browser. A child that dies on its own (a watcher on `ClientSession.Wait`) is dropped the same way, session untouched. Stopping a child is the SDK's stdio close (stdin, then SIGTERM, then SIGKILL, `browserMCPTerminate` apart) followed by a SIGKILL to its process group (`Setpgid`, plus `Pdeathsig` on linux like Chromium's) and a `Wait` when the SDK's close did not reap it — `Client.Connect` returns an unsupported-version failure without closing its transport. Idle stop rarely fires under a child anyway: a child that has connected holds a `/cdp` websocket, and that is an in-flight request.
- **It dials lasso's OWN `/cdp`, never Chromium's port.** `/cdp` is stable across restarts, starts the browser lazily, and its in-flight counter is what keeps the idle stop off while an agent is connected. The address is the one the main listener actually bound (`setListenAddr` after `listenWithFallback`; an unspecified bind is dialed on 127.0.0.1), `ws://` since it is lasso's own listener; `/cdp/p/<id>` for a browser other than the default.
- **The internal token** (`internalCDPToken`, cdpproxy.go): 32 bytes from `crypto/rand` per process, memory only, never logged, handed to the child as `--wsHeaders '{"X-Lasso-Internal":…}'` and stripped before the proxy talks to Chromium. The agent's credential stops at `/mcp`; the child is lasso's own process and has nothing else to present. `withInternalCDP` wraps the OUTERMOST handler, not `withCDPAuth`, because with `-require-access-header` a loopback dial from the child carries no Cloudflare identity and the Access gate would refuse it before `withCDPAuth` ran; it matches `/cdp` paths only (constant-time), so the token opens nothing else, and `serveCDP` still applies the Origin guard. It rides argv because chrome-devtools-mcp reads websocket headers from nowhere else; argv is world-readable on the box — measured, briefly: the child sets `process.title`, after which `/proc/<pid>/cmdline` reads just `chrome-devtools-mcp` — which is no worse than a loopback lasso's open `/cdp` to the same users.
- **The gate: `/cdp`'s standard, per call** (`withBrowserToolGate`, `browserRequestRefusal`, `browserToolRefusal`). A browser tool is a front door to `/cdp` — its child gets through on the internal token — so a call must meet `/cdp`'s standard, and `/mcp`'s is weaker: `/mcp` is open under UI_AUTH alone, and takes a request with any Origin. The rule, applied to each `browser_*` call:
  - **the Origin guard first**: no Origin (a CLI or agent's MCP client) or lasso's own origin only (`cdpOriginAllowed`), so no web page a user visits can drive a browser through a loopback lasso. `null` is foreign. This holds with any credentials.
  - **MCP_OAUTH set**: what `/mcp` accepts (`withMCPAuth` has already required a lasso bearer token or the UI_AUTH basic credentials), and a token's reach must include `local`, where the browsers run (`requireLocalBrowser`, the rule `cdpScopeCheck` applies to `/cdp`).
  - **only UI_AUTH set**: its basic credentials on the MCP connection — which `/mcp`'s other tools do not ask for and `/cdp` does.
  - **neither**: open, `/mcp`'s and `/cdp`'s trust model.

  There is no same-origin-page allowance like `/cdp`'s: no page of lasso's speaks MCP. A tool handler does not get the HTTP request — the go-sdk hands it the headers and the TokenInfo, not the Origin's comparison with the Host, nor the configured credentials — so `withBrowserToolGate`, inside `withMCPAuth` on every `/mcp` request, computes the verdict there and stamps it into the headers the SDK copies onto each call's `Extra`: `X-Lasso-Browser-Gate` = `browserGateToken` (32 random bytes per process, distinct from the internal CDP token) when the request passes, `X-Lasso-Browser-Refusal` = the reason when it does not. Both are deleted and set on every request, so a client cannot supply either; the value is a secret rather than a flag so that a path to the server that skipped the wrapper fails closed. The handler (`forward`) checks the stamp in constant time, then `requireLocalBrowser`, and answers a failure as a tool error (`isError`) naming what is missing, before anything spawns. `tools/list` still shows the browser tools to every caller — the list is one per server — and calling one is what is refused. lasso's other browser tools (`list_browsers`, the tab tools, `shared_browser`) keep `/mcp`'s gate plus `requireLocalBrowser`: they manage browsers and pages, they do not read or type into one. Cloudflare Access (`gate.wrap`) fronts all of it.
- **The child's flags are lasso's** (`browserMCPArgs`, then whitespace-split `LASSO_BROWSER_MCP_ARGS`, a later duplicate winning in yargs): `--wsEndpoint`/`--wsHeaders` above; `--no-usage-statistics --no-performance-crux` (the URLs an agent visits are nobody's telemetry); `--screenshotFormat jpeg --screenshotQuality 80 --screenshotMaxWidth 1280 --screenshotMaxHeight 1280`, because the browser renders at `-browser-scale` 2 and an unbounded PNG costs an agent ~4x the image tokens (measured through the bridge: example.com comes back 1280x713 JPEG, ~17 KB). chrome-devtools-mcp ≥1.10 defaults to `--pageIdRouting`, so page-scoped tools (e.g. `browser_take_screenshot`) want a `pageId` from `browser_list_pages`/`browser_new_page`; lasso leaves that default alone.
- **Its environment is an allowlist** (`browserMCPEnv`): PATH, HOME, locale, TMPDIR, XDG dirs, mise's directory settings (mise's shims need them to find node; `MISE_GITHUB_TOKEN` is a `MISE_` var too, hence directories only), plus `CHROME_DEVTOOLS_MCP_NO_USAGE_STATISTICS=1`. Never lasso's `UI_AUTH`/`MCP_OAUTH`/`LASSO_MCP_TOKEN`, nor anything else the operator's shell exported: this is a process driving arbitrary web pages. Its stderr goes to lasso's log as `browser-mcp[<pid>]:`, at most 30 lines a minute per child, with the tail kept for a startup failure.
- **No `npx` fallback, on purpose.** The binary is `-browser-mcp`/`LASSO_BROWSER_MCP` (a path or PATH name; `off` → no browser tools, with the reason) or `chrome-devtools-mcp` on PATH. Fetching an unpinned package from the registry at runtime, on the machine holding the browsers' logged-in profiles, is a supply-chain hole; the docs tell the operator to `npm i -g chrome-devtools-mcp` or `mise use -g npm:chrome-devtools-mcp`.
- **`lasso connect`** registers `lasso` (`/mcp`, which carries the browser tools) and `lasso-herdr`, and removes an entry named `lasso-browser` wherever it finds one: that entry names a `/browser-mcp` URL lasso does not serve, and a dead MCP server in a CLI's config is an error at every agent start.
- **Tests fake the child without node**: `TestMain` re-execs the test binary as a stdio MCP server when `LASSO_TEST_FAKE_BROWSER_MCP` is set (`browsermcp_test.go`), passed through the bridge's `ExtraEnv` seam since the child's environment is otherwise an allowlist. The tests serve `/mcp` wired exactly as `main` wires it (`withMCPAuth(withBrowserToolGate(withRequestBase(newMCPHandler())))`), so the gate tests exercise the real path: no credentials under UI_AUTH, a remote-scoped token under MCP_OAUTH, a foreign or `null` Origin, a forged gate header.

### Terminal links

**Terminal links open in the Browser tab by default** (`lib/sidebar-browser.ts`, `wireLinkOpen` in `lib/terminal.ts`; Settings → General, `ui_state.terminal_links_in_sidebar`). xterm opens both a detected URL and an OSC 8 hyperlink as `window.open()` with no URL, then `location.href = url`, so the terminal document's `open` returns a stand-in whose href setter routes the link. Cmd/Ctrl-click keeps a new tab.

- **A link opens in Iframe (Embed), whatever the stored mode** (`sidebarLinkMode`). A terminal link is the human's own page, not one to put in front of every agent sharing the Chromium. Like an agent's `show_browser_tab` forcing Live, it is a per-client override in `BrowserTab` (`override`), never a write to `ui_state.browser_mode`, and any click on the mode switch drops it. The one exception is mixed content: an `http://` link on an https lasso cannot be embedded, so it goes to Live when Chromium is available (`setLiveBrowserAvailable`, published by `BrowserTab`; false until the tab first renders) and to a new tab otherwise.
- **In Live a link loads into the page on screen** (`Page.navigate`; with no page yet, `navigate` opens one). One page at a time is the point: a link stacking up an invisible page per click would be pages nobody can see. `BrowserTab` holds the request (`OpenRequest`) until whichever mode ends up on screen takes it, because a link clicked before `/api/browser` answers is aimed at Live and must still land if the answer is "no Chromium"; Live parks it (`pendingOpen`) until its socket is up.
